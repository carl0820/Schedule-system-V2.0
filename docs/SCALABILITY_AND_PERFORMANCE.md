# 系统可扩展性和性能说明

## 一、支持规模

### 1. 机器人数量支持

系统理论上可以支持**任意数量的机器人**，但实际性能取决于：

- **硬件资源**：CPU、内存、网络带宽
- **网络延迟**：与机器人通信的延迟
- **任务复杂度**：任务数量、路径规划复杂度

**推荐配置**：
- **3-5台机器人**：推荐配置，性能最优
- **6-8台机器人**：可支持，但需要优化网络和硬件
- **9台以上**：需要更强的硬件和网络环境

### 2. 限行区域数量支持

系统理论上可以支持**任意数量的限行区域**，没有硬编码限制。

**容量计算**：
- 每个限行区域的容量根据 `half_width` 计算：
  ```python
  capacity = int(half_width * 2 / ROBOT_CAPACITY_PER_METER)
  # ROBOT_CAPACITY_PER_METER = 0.9 米/机器人
  ```
- 例如：`half_width = 1.0` 米 → 容量 = `int(1.0 * 2 / 0.9) = 2` 台机器人

**推荐配置**：
- **1-3个限行区域**：推荐配置，性能最优
- **4-6个限行区域**：可支持，但需要监控性能
- **7个以上**：需要更强的硬件和网络环境

## 二、性能优化

### 1. 任务分配效率优化

#### 问题
当机器人数量增加到4台以上时，任务分配效率可能下降，原因：
- 需要查询所有机器人的状态
- 需要为每个机器人计算路径成本
- 调度循环可能被阻塞

#### 优化措施

**已实现的优化**：
1. **状态缓存机制**：
   - 使用缓存状态，避免重复查询
   - 缓存有效期：3秒（可配置）
   - 只更新需要更新的机器人状态

2. **并发查询**：
   - 使用 `asyncio.gather` 并发查询多个机器人状态
   - 超时保护：1秒（避免单个机器人阻塞）

3. **事件驱动调度**：
   - 新任务创建时立即触发调度检查
   - 超时时间：0.01秒（快速响应）

4. **智能过滤**：
   - 预先过滤离线、停用、有故障的机器人
   - 只对可用机器人进行成本计算

**性能指标**：
- **3台机器人**：任务分配延迟 < 0.5秒
- **4-5台机器人**：任务分配延迟 < 1.0秒
- **6-8台机器人**：任务分配延迟 < 2.0秒

### 2. 等待点恢复延迟优化

#### 问题
机器人到达等待点后，限行区域释放时，任务恢复可能有延迟（1-2秒）。

#### 优化措施

**已实现的优化**：
1. **立即触发机制**：
   - 限行区域释放时，立即调用 `_check_and_resume_waiting_robots()`
   - 触发调度事件，确保任务立即被处理

2. **双重检查机制**：
   - `check_waiting_robots` 内部调用恢复逻辑
   - `_update_executing_tasks` 也调用恢复逻辑
   - 确保没有遗漏

3. **状态同步**：
   - 机器人移到通行列表时，立即清除等待状态
   - 清除 `action_id`，准备重新执行

**性能指标**：
- **恢复延迟**：< 0.5秒（从限行区域释放到任务恢复）

### 3. 死锁检测和解锁支持规模

#### 死锁检测

**支持的死锁类型**：
1. **限行区域死锁**：容量超限
2. **资源竞争**：单个机器人卡住
3. **循环等待**：多台机器人形成循环（已移除，由限行区域机制处理）
4. **相互阻塞**：多台机器人面对面阻塞（已移除，由限行区域机制处理）

**检测频率**：
- **死锁检测循环**：每0.5秒检测一次（2Hz）
- **限行区域监测**：每次 `_update_executing_tasks` 调用时检测

**支持规模**：
- **机器人数量**：理论上无限制，但建议 ≤ 8台（性能考虑）
- **限行区域数量**：理论上无限制，但建议 ≤ 6个（性能考虑）

#### 解锁机制

**解锁策略**：
- **2-3台机器人**：让1台低优先级机器人后退或移动到等待点
- **4-5台机器人**：让一半（2-3台）低优先级机器人后退或移动到等待点
- **6台或更多**：让1/3的低优先级机器人后退或移动到等待点

**解锁频率**：
- **死锁持续时间阈值**：
  - 限行区域死锁：立即触发（容量超限时）
  - 资源竞争：5秒
  - 其他类型：根据配置

**支持规模**：
- **同时处理的死锁数量**：理论上无限制
- **解锁机器人数量**：根据策略动态计算

## 三、性能监控

### 1. 关键指标

**任务分配指标**：
- 任务创建到分配的时间（`_task_creation_timestamps`）
- 可用机器人数量
- 待分配任务数量

**等待点恢复指标**：
- 限行区域释放到任务恢复的时间
- 等待队列长度
- 通行列表长度

**死锁检测指标**：
- 死锁检测频率
- 死锁持续时间
- 解锁成功率

### 2. 日志级别

**DEBUG级别**：
- 详细的调度循环信息
- 机器人状态查询
- 路径规划结果

**INFO级别**：
- 任务分配成功/失败
- 等待点恢复
- 死锁检测和解锁

**WARNING级别**：
- 任务分配超时
- 等待点恢复失败
- 死锁解锁失败

### 3. 性能调优建议

**如果任务分配效率低**：
1. 检查网络延迟（机器人通信）
2. 增加状态缓存时间（减少查询频率）
3. 减少路径规划复杂度
4. 使用更快的硬件

**如果等待点恢复延迟**：
1. 检查 `check_waiting_robots` 调用频率
2. 检查调度事件是否正常触发
3. 检查任务状态是否正常更新

**如果死锁检测不准确**：
1. 检查限行区域配置（容量、等待点）
2. 检查机器人状态更新频率
3. 检查死锁检测循环是否正常运行

## 四、已知限制

### 1. 硬件限制

- **CPU**：建议 ≥ 4核（多机器人并发查询）
- **内存**：建议 ≥ 4GB（状态缓存、路径规划）
- **网络**：建议延迟 < 100ms（机器人通信）

### 2. 软件限制

- **Python版本**：≥ 3.11（异步性能优化）
- **asyncio并发数**：受系统限制（默认通常足够）

### 3. 配置限制

- **调度循环超时**：0.01秒（事件驱动）
- **状态缓存时间**：3秒（可调整）
- **机器人查询超时**：1秒（可调整）

## 五、未来优化方向

1. **分布式调度**：支持多调度器实例
2. **智能预测**：预测机器人可用时间，提前分配任务
3. **动态优先级**：根据等待时间动态调整优先级
4. **路径缓存**：缓存常用路径，减少规划时间
5. **批量查询**：批量查询机器人状态，减少网络开销
